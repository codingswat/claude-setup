# Writing UI copy under the honesty test

## Overview

A sentence earns its place only where the user has no way to reach it by guessing or
inferring — being true is not enough on its own. Keep copy as structured values in the
source that renders it, not scattered string literals.

## When to use / when not

Any user-facing string in your app's front end or server responses. Not comments, internal
docs, or copy generated by a separate content system with its own review process.

## Quick reference — per sentence

| The sentence | Verdict |
|---|---|
| Inferable, already shown elsewhere on this screen, or borderline | **CUT** |
| Half implied, half surprising | **TRIM** to the surprising half |
| Qualifies a number the user is about to trust (an estimate, an assumption, a confidence grade) | **KEEP** |
| A consequence the user would act on — unrecoverable, spent, expires — or explains a refusal | **KEEP** |

The rule, close to verbatim: *if there's no way the user can guess or infer that piece of
information, and only then, it should be written.* Tie-break on anything borderline: start
with too few words, not too many — add a sentence back later, with evidence it's needed,
rather than trimming one out later that never should have shipped.

The unconditional keeps, not reachable by any lean-copy instinct (a number shown without its
caveat is a wrong number):
- anything qualifying a number the user is about to trust;
- anything explaining why something was refused;
- the consequence a user would act on: unrecoverable, spent, expires, limited.

These sentences are moved and made visually quieter, never hidden: keep them at the point of
use, smaller than the number they qualify, never collapsed behind a "show more."

## Required slots — output missing any of these is unfinished

1. **One structured object holding every string** (for example
   `const COPY = {...} satisfies Record<string, ...>` in the file that renders it), not
   string literals scattered through the component. If your product supports one language,
   this still matters — it's what makes the rules below checkable by a test. If it supports
   more than one, every key carries a real, human-reviewed string per language — not a
   placeholder and not a machine translation nobody read — and a test asserts every key has
   every language filled in; a key missing one language is invisible until a native reader
   happens to notice.
2. **A comment above the object naming the code that makes each claim true.** A claim you
   can't point at a specific piece of enforcing code for is a claim you shouldn't be
   writing.
3. **The check (a lint rule, a test) that polices these strings, named** — plus whatever new
   assertion the new copy needs.
4. If more than one language: real, reviewed text in every one of them, not stand-ins.

## Never

- **Internal or technical vocabulary** the user has never seen and can't act on — the name
  of your server, your database, your internal data format, jargon that describes your
  implementation rather than the user's situation. If something is unreachable, say what the
  user can actually do about it, not which internal component failed.
- **Marketing or reassurance language.** In a full-screen copy audit run against this rule,
  honest, load-bearing copy (numbers' caveats, refusals, consequences) made up the clear
  majority of user-facing words, and reassurance or marketing copy made up effectively none
  — cutting what's inferable and keeping only what's load-bearing are not in tension.
- **A disclosure hidden behind "show more," or cut purely for length.** Length is never the
  reason a load-bearing sentence goes.

## Rationalizations that fail here

| Thought | Reality |
|---|---|
| "It's true, so it stays." | The bar is inferability, not correctness. |
| "It reassures the user." | Reassurance is usually inferable; it isn't a category this rule protects. |
| "I'll trim it later." | Start with too few; add back later with a reason. |
| "I'll wire it up properly later." | Copy that isn't in the checked structure yet is exactly the drift this rule exists to stop. |

## The example

```ts
// Claim → enforcement: nothing leaves this device — see the local-storage module.
const COPY = {
  keepACopy: {
    en: "We don't keep a copy of your file, so if this device loses it, we can't get it back for you.",
  },
} satisfies Record<string, LocalizedString>;
```

"Saved on this device only" was CUT here — it's implied by the sentence that follows it.
"Nobody can get it back" survived: it's the fact that should make someone take their own
backup.

## Common mistakes

- A success screen saying only that it succeeded — the screen already said that by
  existing.
- Promising behavior ("works on any device") with no code path that actually makes it true.
- Reusing a stock button label the code contradicts — for example "Continue without saving"
  on a screen where the data IS saved locally and only a secondary sync step failed. The
  honesty test binds labels too, not just sentences: trace the claim to the actual code path
  before reusing a familiar label.
